# AI原生操作系统架构（v2 · 讨论校订版）

> 本版是在与实现代码逐条核对、并厘清若干概念误区后重写的。
> 与 v1 的主要区别：区分了"论文实验代码"与"实际运行时"；纠正了"改造 Linux 内核"的措辞；
> 引入"行动平面 / 策略平面"的拆分；重新定位了 eBPF 的角色（策略强制，而非动作执行）。

---

## 一、核心理解（校订版）

**一句话构想**：

> 在 **未改动的** Linux 之上叠一层 AI 原生控制平面。用 MCP/Skills 把系统资源封装成
> **带能力门控的设备**；LLM 把自然语言编译成 **LIR**，LIR 确定性编译成 **M-Token 字节码**，
> 在 **MVM**（M 语言虚拟机）上有界执行。MCU 与本机走的是**同一条链**，区别只是 MVM
> 在串口远端（MCU）还是在本地（PC）。

**三条已确认的等价关系**（论文术语 = 代码术语）：

| 论文术语 | 代码术语 | 本质 |
|----------|----------|------|
| LIR (源语言) | M-IR | LLM 生成的、结构化、人类可读的控制中间语言 |
| M-Token | bytecode | LIR 确定性编译出的紧凑字节码，是执行格式 |
| LVM | MVM | 执行 M-Token 的有界安全虚拟机 |

**关键澄清（相较 v1 的修正）**：

1. **Linux 内核不需要改动**。整套东西（LLM、MCP、Skills、MVM）都在用户空间，
   站在原装 Linux 上。这不是能力上限，而是刻意选择：可装在任何普通 Linux 上，无需重编内核。
   （若未来要把策略强制下沉内核，见第五节 eBPF——但那是演进方向，不是前提。）
2. **LIR 从不"直接执行"**。它永远先编成 M-Token，再由某台 MVM 执行。
   "控制本机"也是 `LIR → M-Token → 本地 MVM`，只是少了串口那一跳。
3. **"操控计算机"的本质是发 syscall**。当前 M-Token 指令集对外只有 `IOW/IOR` 两条，
   只认 `device_id`——它今天**只能碰硬件设备口，碰不到文件/进程/网络**。
   要让这条链够到本机资源，必须先把 PC 资源"设备化"或"能力化"（见第三、四节）。

## 二、当前实现的真实状态（重要：勿高估）

与代码核对后的事实，避免把"论文实验代码"误读为"已上线能力"：

| 组件 | 位置 | 状态 |
|------|------|------|
| M-Token VM（C） | `src/m_vm.c` 等 | ✅ 真实、完整，80+ 指令 |
| ESP8266 MVM 固件 | `firmware/mvm_esp8266.ino` | ✅ 真实，串口执行字节码 |
| LIR 编译器 | `论文分区/ccfc/tools/mir_compiler.py` | ✅ 真实（882 行），但**仅用于论文实验** |
| LVM 参考实现 | `论文分区/ccfc/tools/backend_adapter.py` | ✅ 真实，**仅用于论文实验** |
| MCP 工具层 + Skills | `python/MCP/*.py` | ✅ 真实，25+ 工具 |

**必须正视的断点**：

- 正在运行的系统（`python/MCP/server.py` + `tool-router/router.py`）
  **从未 import 过 `mir_compiler`**。运行时走的是 **tool call**，LLM **从未生成过一行 LIR**。
- 因此存在**两个平行系统**：一个是论文里跑 benchmark 的 LIR 系统，一个是线上用
  tool call 的 MCP 系统，**中间是断的**。
- 你构想里最独特的那句"把 2KB 上抗攻击的安全核心放大成 OS 脊梁"，
  **恰恰是唯一还没进主干的部分**。这是"核心假设已在实验室验证，但尚未接入运行时"，
  不是"已实现待优化"。

**M-Token 目前的三代产生方式**（并存）：

1. 人手写 token（如 `relay_set_mcp`）——安全但死板，token 是程序员写的。
2. LLM 裸吐 token（`execute_m_logic_mcp`，如 `[80,1,71,1,82]`）——灵活但危险，
   `core.py` 里那一大段 `common AI mistake` 防御就是为它擦屁股。
3. LIR（`mir_compiler`）——又灵活又安全，把安全检查从**运行时**提前到**编译期**，
   但**还没接进运行时**。第三代是终点，缺的就是把它接上、替换掉第二代。

## 三、术语与数据流

### 3.1 完整闭环（硬件控制示例）

**用户说**："帮我开风扇，盯着温度，到 25 度告诉我"

```
自然语言
  │  ① LLM 理解意图
  ▼
LIR 文本（LLM 生成，人类可审）
  task cool_room {
    require cap(relay1)
    require cap(temperature_sensor)
    set relay1 = 1
    retry 100 times {
      wait 1000ms
      readback temperature_sensor expect 25
    }
    halt
  }
  │  ② mir_compiler 确定性编译（编译期静态验证：能力前置、跳转偏移自动计算）
  ▼
M-Token 字节码
  GTWAY 5; GTWAY 2; LIT 1; IOW 5; ... JZ -10; HALT
  │  ③ 发送到 MVM
  ▼
MVM 执行（能力门控 / 步数限制 / gas / 调用深度）
  ├─ 本机：本地 MVM 直接执行
  └─ MCU：经串口 [4B LE len][varint bytecode] → ESP8266 固件执行
  │  ④ 结果沿原路返回
  ▼
LLM 用自然语言反馈用户："温度已到 25 度，风扇已关。"
```

### 3.2 MVM 是"安全闸门"

```
字节码 → 静态验证 → 能力门控 → 步数/gas 限制 → 执行
                        ├─ 无能力     → M_FAULT_UNAUTHORIZED
                        ├─ 超步数     → M_FAULT_STEP_LIMIT
                        └─ gas 耗尽   → M_FAULT_GAS_EXHAUSTED
```

## 四、控制本机：把 PC 资源"设备化"（路线 A）

MVM 对外只有 `IOW/IOR`，只认 `device_id`。要控制本机而**不改 MVM**，
就把 PC 的每类资源抽象成一个带 `device_id` 的**虚拟设备**，复用现有 IOW/IOR + GTWAY。

概念映射（示意，非定稿）：

| device_id | 虚拟设备 | IOR（读） | IOW（写） | 能力门控 |
|-----------|----------|-----------|-----------|----------|
| 1–99 | 物理硬件（现状） | 传感器 | 继电器 | 已有 |
| 100 | 文件句柄 | 读一块 | 写一块 | `cap(file:/path)` |
| 110 | 进程 | 读退出码/输出 | 起/杀进程 | `cap(proc:name)` |
| 120 | 网络 | 收 | 发 | `cap(net:host:port)` |

**难点：IOW/IOR 一次只传一个整数，字符串（路径/进程名）怎么办？**

- **选择一（推荐）**：复杂参数放进 LIR 的 `require cap(file:/tmp/x)` **前置声明**，编译期就固定；
  运行时 IOW 只传"第几个已声明资源 + 值"。字节码里不出现字符串，
  **保住"能力前置声明、编译期可审、清单静态锁死"这一核心优势**。它与 LIR 现有
  `require cap(...)` 语义天然吻合。
- **选择二**：给 MVM 加字符串常量池——会让 MVM 变重，MCU 上未必跑得动，破坏"同一条链"。不推荐。

## 五、eBPF 的正确定位：策略强制平面，不是动作执行引擎

（这一节纠正一个常见误解，是本架构最硬的原创点所在。）

**误区**：把 LIR 编译成 eBPF 字节码、靠内核 JIT 出机器码来"高性能执行动作"。
这条路走不通，因为它误解了 eBPF 是什么：

1. **eBPF 不能控制计算机**——不能 `open/fork/execve/sys_write`，只能调用内核给的
   **固定 helper 白名单**。这是它的设计目的，不是没做完。
2. **eBPF 不是"跑程序"，是"挂钩子"**——必须 attach 到 hook 点（kprobe/tracepoint/LSM/XDP…），
   事件触发才执行。命令式的 `task {...}` 流程没有对应的"运行"模型。
3. **不能阻塞睡眠**——`wait 1000ms` 这个 LIR 核心原语直接失效。
4. **验证器会拒收通用程序**——无界循环、超指令数、任意内存/调用都被否决。
   带 retry/wait/任意 IO 的 LIR 会被**当场拒绝**。你以为它帮你做静态分析，其实它在挡你。
5. **性能是伪需求**——继电器/传感器动作在毫秒到秒级，解释器那点微秒开销不可测量。
   JIT 对硬件控制**零收益**（跨架构自动出 x86/ARM 机器码这点是真收益，但与"控制动作"无关）。

**正解：区分两个平面，eBPF 只属于策略平面。**

| 平面 | 职责 | 由谁执行 |
|------|------|----------|
| **行动平面 Action** | 真去开文件 / 起进程 / 发包 | 用户空间 LIR 运行时 → **真实 syscall**（即"PC 版 MVM"） |
| **策略平面 Policy** | 门控 / 观测系统里发生的一切 | LIR → **eBPF**（LSM-BPF / seccomp-bpf），注入内核强制执行 |

- **"控制计算机"只能在行动平面完成**，用普通用户空间运行时发真 syscall（参照 JVM/Python
  解释器——都在用户空间，照样完整操控计算机）。eBPF 在此帮不上忙。
- **eBPF 字面意义（而非类比）大放异彩的地方是策略平面**：把 LIR 编译成 seccomp/LSM-BPF，
  对全系统每个 syscall 做**不可伪造、不可绕过**的能力门控。seccomp-bpf 本就是用小段字节码
  门控每个 syscall，和 GTWAY 思想一模一样，且解决了用户空间门控**能被绕过**的根本弱点。

**由此得到的论文级原创点**：

> LLM 每生成一段 LIR，系统**同时编译出两套产物**：
> ① 用户空间执行的**动作字节码**（要做什么）；
> ② 注入内核的 **eBPF 能力策略**（内核层面被允许做什么）。
> 后者由内核验证器与 JIT 强制执行，不可伪造、不可绕过。
> 这样"eBPF 之于 LIR，如 seccomp 之于 syscall"**不是类比，是实现**。

## 六、双后端 + 双平面 · 统一架构全景

```
                          用户自然语言
                               │
                               ▼
                        LLM 大脑（Ollama）
                               │ 生成 LIR 文本
                               ▼
                    mir_compiler（确定性编译 + 编译期静态验证）
                       │                         │
        ┌──────────────┘                         └──────────────┐
        ▼ 动作产物                                        ▼ 策略产物
   M-Token 字节码                                    eBPF 能力策略
        │                                                 │ bpf() 加载
   ┌────┴─────────────┐                                   ▼
   ▼ 后端A（MCU）      ▼ 后端B（PC/服务器）          Linux 内核
 串口→ESP8266         本地用户空间 MVM              ├─ 验证器（有界/内存安全）
 轻量解释器           发真 syscall 控制本机          ├─ JIT（x86/ARM/RISC-V）
 （2KB 环境）         （文件/进程/网络，路线A设备化） └─ LSM-BPF/seccomp 强制门控
        │                     │                            │
        └──────── 硬件 / 系统资源 ◄───────────────────────┘
                               │
     ┌─────────────────────────┴──────────────────────────┐
     │            未改动的 Linux 内核（用户空间之下）        │
     │   进程调度 | 内存 | 文件系统 | 驱动 | 提供 syscall/eBPF │
     └──────────────────────────────────────────────────────┘
```

- **后端 A（物理设备端）**：LIR → M-Token → ESP8266 轻量解释器。适合 2KB 受限环境。
- **后端 B（高性能端）**：LIR → M-Token → 本地用户空间 MVM，发真 syscall 控制本机。
- **策略平面（贯穿全系统）**：LIR → eBPF，注入内核对 syscall 做强制能力门控。
- **唯一桥梁**：同一套 LIR 语法，统一了"微控制器级实时控制"与"服务器级系统控制"。
